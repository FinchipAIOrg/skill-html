ONTOLOGY

一个给 AI Agent 的 Skill

记得住文字，
记不住关系？

给 Agent 的记忆装一副骨架。用 create 和 relate 把人、项目、任务存成 16 类实体与 15 类关系，再用一次 validate 检查必填、枚举、禁填、基数、无环。 你得到的不是又一份 Markdown，而是一张能追问、能遍历、也能被别的 Skill 直接读写的图。

16 类实体 15 类关系 5 类约束 MIT-0
前往官方 Skill 页面 → GitHub 仓库

一条命令接入 · 开源免费 · 需要 Python 3.10 及以上

TERMINAL · 本次会话真实命令
$ ontology create --type Person --props '{"name":"Alice"}'
→ pers_b1124baf
$ ontology create --type Project --props '{"name":"官网改版","status":"active"}'
→ proj_8a0b4a79
$ ontology create --type Task --props '{"title":"重写首页文案","status":"open"}'
→ task_cfe03b86
$ ontology relate --from proj_8a0b4a79 --rel has_task --to task_cfe03b86
$ ontology relate --from proj_8a0b4a79 --rel has_owner --to pers_b1124baf
$ ontology relate --from task_cfe03b86 --rel assigned_to --to pers_b1124baf
$ ontology validate
✓ Graph is valid.

Before / After

从在文字里翻关系，
到沿一条命名关系直接取回答案

右栏的 Prompt 与 Output 均为本次会话实际运行所得，逐字引用，未做修饰。

BEFORE用 Skill 之前
  • ✕记忆是一段段文本，关系靠脑补。写着"Alice 负责官网改版"，但"负责"是负责人、执行人还是被顺带提到，机器读不出来。
  • ✕状态字段想怎么写怎么写。同一个状态写成"进行中""doing""in progress"三种样子，等下游技能读到才出问题。
  • ✕每个技能各存各的文件。邮件技能写下的承诺，任务技能根本读不到，只能手写转换代码，或者你自己当搬运工。
  • ✕问一句关系，翻一遍历史。想确认"这个项目谁负责"，只能翻聊天记录，靠关键词碰运气。
  • ✕上下文一关，关系就没了。下次开会前还得重新讲一遍谁负责什么、什么卡着什么。

03

Core Capabilities

六件事，它替你做扎实

实体类型与关系类型数量来自技能自带的 schema 参考文档，逐条清点。

01

带类型的实体

Person、Project、Task、Event、Document、Credential 等 16 类，每类都有明确的必填字段与属性类型，不是随便塞进去的一段话。

16 类必填字段ref 引用
02

命名关系

15 类关系各自声明从什么类型连到什么类型。has_owner、has_task、blocks 不是字符串标签，是可遍历、可校验的边。

15 类正向遍历反向遍历
03

五类约束

必填、枚举、禁填、基数、无环。秘钥类实体强制只存 secret_ref，明文 password 会被点名拦下。

必填枚举禁填基数无环
04

一次体检列全

validate 报出实体 id、字段名和具体原因，而不是笼统一句"数据有问题"。实测中五类违规在同一次调用里被分别点名。

validate定位到 id
05

跨技能共享

每个技能声明读哪些类型、写哪些类型，共享同一份图谱。新增技能不必改动已有技能，也不会改坏已有数据格式。

readswrites无需胶水代码
06

两个纯文本文件

只落进工作区的 graph.jsonl 与 schema.yaml。JSONL 一行一次操作，可 diff、可回滚、可进版本库。脚本不联网，不读身份与凭据文件。

graph.jsonlschema.yaml可 diff
需要说清楚的边界

create 和 relate 写入时不拦截，违规数据会先落盘，由 validate 统一检查。这一点在实测中已确认：缺必填字段和错误枚举值都成功写入，随后才被 validate 报出。想要写入即校验，需要在外面再包一层。

另外，文档里提到的任务状态流转校验与孤立任务告警，在当前代码中尚未实现。无环约束需要在 schema 中显式声明才会生效。

三个实体三条关系，一次建起来

$ ontology validate

    "entity": {
      "id": "task_cfe03b86",

为什么重要：问"这个项目的负责人是谁"，走一条关系就有答案，不必再翻历史记录。遍历可以正向也可以反向。

05

How It Works

五步，从零到一张能校验的图

你提供实体和关系，Skill 按类型写进工作区，每行一次操作，追加而不是覆盖。

1

定规则

用 schema-append 写入必填字段、枚举取值、禁填字段、关系基数和是否要求无环。

schema-append --data '{...}'
2

建实体

指定类型和属性，返回带 id 与创建时间的实体。

create --type Person --props '{"name":"Alice"}'
3

连关系

关系类型来自 15 类预定义关系，各自限定了从什么类型连到什么类型。

relate --from proj_xxx --rel has_owner --to pers_xxx
4

取答案

query 按类型条件筛，get 按 id 取，related 沿某类关系遍历。

related --id proj_xxx --rel has_task
5

做体检

一次列出全部违规，指出实体 id、字段名和具体原因。

validate
graph.jsonl → schema.yaml → 可 diff · 可回滚 · 可进版本库
06

Who & When

谁该用它，用在什么场景

搭多 Agent 系统的开发者

PRIMARY USER

你要让几个技能接力完成一条流程：抓公告的技能产出的东西，分析技能要能直接用；分析技能写下的结论，报告技能要能取到。现在这些衔接全靠手工拼。

  • 抓公告 → 建实体 → 触发分析 → 生成报告
  • 多个技能通过图谱交换状态，不靠传参
  • 新增技能不必改动已有技能

受够了反复重讲的进阶用户

SECONDARY USER

你的 Agent 记得住零散事实，却答不出"谁在负责这件事"。每次新开会话，关系和上下文都要重讲一遍，讲过的内容散落在几十条记忆里，越积越难找。

  • 长期人物与项目档案，跨会话保持
  • 多步任务规划，依赖可查无环
  • 邮件承诺追踪，链条可追溯
场景 长期人物 / 项目档案 → 人、组织、项目互联互通，"这个项目谁负责"一跳就到
场景 多步任务规划 → 计划建模成一串图操作，每步可校验，依赖能查无环
场景 跨技能协作 → 技能间通过图共享状态，不靠传参
场景 联系人 / 日程管理 → Event、Location、attendee 关系天然适合

ONTOLOGY

给 Agent 的记忆装一副骨架。记住关系，不只是记住文字。

clawhub.ai/oswalpalash/skills/ontology

你要提供的：想让 Agent 记住的实体，以及它们之间的对应关系。可选再补一份规则，指定哪些字段必填、状态只能取哪些值。

你会得到的：一张持久化、可校验、能被别的 Skill 直接读写的知识图谱，外加一份随时可体检的规则文件。
