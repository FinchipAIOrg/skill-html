ONTOLOGY

A skill for AI agents

It remembers the text.
It forgets the relationships.

Ontology gives your agent's memory a skeleton. Use create and relate to store people, projects, and tasks as 16 typed entities joined by 15 named relations — then run one validate pass to check required fields, enums, forbidden properties, cardinality, and cycles. You do not get another Markdown file. You get a graph you can traverse, diff, and hand to another skill as-is.

16 entity types 15 relation types 5 constraint classes MIT-0

BEFOREBefore the skill
  • ✕Memory is prose; relationships are implied. The note says "Alice owns the website redesign" — owner, assignee, or merely mentioned? The machine cannot tell.
  • ✕Status fields are free text. One state gets written as "in progress", "doing", and "wip". The downstream skill finds out when it already broke.
  • ✕Every skill keeps its own files. A commitment written by the email skill is invisible to the task skill — so you write a converter, or copy the data by hand.
  • ✕Answering a relationship question means re-reading history. "Who owns this project?" turns into a keyword search across old transcripts.
  • ✕Close the context, lose the structure. Every new session starts with re-explaining who owns what and what is blocked by what.

Core Capabilities

Six things it does properly

Entity and relation counts come from the skill's own schema reference, checked one by one.

01

Typed entities

Person, Project, Task, Event, Document, Credential and ten more. Each type declares its required fields and property types, so a record is a record — not a paragraph.

16 typesrequired fieldsref links
02

Named relations

15 relation types, each declaring what it may connect to what. has_owner, has_task, and blocks are not string labels — they are traversable, checkable edges.

15 typesforward walkreverse walk
03

Five constraint classes

Required, enum, forbidden, cardinality, acyclic. Credential entities are forced to store a secret reference only — a plaintext password is flagged by name.

requiredenumforbiddencardinalityacyclic
04

One pass, every violation

validate reports the entity id, the field name, and the cause — not a generic "something is wrong". In testing, all five classes were reported in a single call.

validateid-level detail
05

Shared across skills

Each skill declares which types it reads and which it writes, and all of them share one graph. Add a skill without touching the others or breaking their data format.

readswritesno glue code
06

Two plain text files

Everything lands in graph.jsonl and schema.yaml inside your workspace. One line per operation: diffable, revertible, version-controllable. The script makes no network calls and reads no credential files.

graph.jsonlschema.yamldiffable
WHERE THE LIMITS ARE

create and relate do not validate on write. Invalid data is committed first and caught afterwards by validate — confirmed in testing: a record missing a required field and one holding an out-of-enum value were both written successfully, then reported. If you need validation at write time, wrap the calls.

Two behaviours described in the documentation are not implemented in the current code: task status transition checks and orphan-task warnings. The acyclic constraint only takes effect once the relation is declared in the schema.

How It Works

Five steps from empty to a validated graph

You supply the entities and the relations. The skill writes them into your workspace, one line per operation — appending, never overwriting.

1

Declare the rules

schema-append writes required fields, enum values, forbidden fields, relation cardinality, and whether a relation must stay acyclic.

schema-append --data '{...}'
2

Create entities

Give a type and its properties; get back an entity with an id and a timestamp.

create --type Person --props '{"name":"Alice Chen"}'
3

Connect them

Relation types come from the 15 predefined kinds, each restricting what may connect to what.

relate --from proj_xxx --rel has_owner --to pers_xxx
4

Ask questions

query filters by type and condition, get fetches by id, and related walks a named relation.

related --id proj_xxx --rel has_task
5

Run the check

One pass lists every violation with entity id, field name, and cause.

validate
graph.jsonl → schema.yaml → diffable · revertible · version-controllable

Who & When

Who should use it, and for what

Developers building multi-agent systems

PRIMARY USER

You are wiring several skills into one pipeline: what the announcement-fetching skill produces has to be usable by the analysis skill, and what the analysis skill writes has to be readable by the report skill. Today every one of those handoffs is hand-built.

  • Fetch announcement → create entities → trigger analysis → generate report
  • Skills exchange state through the graph instead of passing arguments
  • Adding a skill does not require changing the existing ones

Power users tired of repeating themselves

SECONDARY USER

Your agent remembers isolated facts but cannot answer "who owns this". Every new session means re-explaining the relationships and the context, and the explanations pile up across dozens of notes until nothing is findable.

  • Long-lived people and project records that survive across sessions
  • Multi-step planning, with dependencies you can check for cycles
  • Commitment tracking from email, with a chain you can trace back
USE CASE Long-lived people & project records → People, organisations, and projects interlinked — "who owns this" is one hop
USE CASE Multi-step task planning → A plan modelled as graph operations; each step checkable, dependencies provably acyclic
USE CASE Cross-skill collaboration → Skills share state through the graph, not through arguments
USE CASE Contacts & scheduling → Event, Location, and attendee relations fit the model natively
