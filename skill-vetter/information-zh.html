关键能力与数据指标

四步协议、14 条红线、
四级裁决，都写死在源码里

skill-vetter 的能力全部由提示词协议定义——没有可执行代码，没有配置项，也不调用任何外部服务。 下面每一个数字都能在那 138 行源码里逐条数出来，不依赖任何运行时统计。

能力 01

四步固定协议

来源核查 → 逐文件读码 → 权限范围 → 风险定级。顺序写死，第二步标注为 MANDATORY， 不允许跳步，也不允许只挑其中一步做。

Step 1来源核查 · 5 问 Step 2代码审查 · 读全部文件（强制） Step 3权限范围 · 5 项 Step 4风险定级 · 4 级
能力 02

14 条「命中即拒」红线

逐条枚举的拒绝条件，覆盖数据外流、凭据越权、隐蔽执行三类典型手法。 这是整份协议里最硬的部分——不需要主观判断，命中即拒。

能力 03

风险定级 → 处置权限

四级风险不是打分，而是回答「这一步谁能拍板」。级别越高， 有权限做决定的人越少——🔴 及以上直接上移给人类，而不是留给 agent 自己拿主意。

工作流程

四步走完，
才轮到「装不装」

协议的顺序写死了：来源核查 → 逐文件审查 → 权限范围 → 风险定级。 每一步都有固定产出物，上一步没做完，不进入下一步。

1
STEP 1 / SOURCE CHECK

来源核查

先问清这个 skill 从哪来、谁写的、有多少人在用。这一步决定的是后面该花多少力气——不是决定装不装。

  • ☐这个 skill 从哪来？
  • ☐作者是否已知 / 可信？
  • ☐有多少下载量 / 星数？
  • ☐最后更新于何时？
  • ☐有没有其他 agent 的评审？
产出一个来源可信度判断，落到下面的 5 级信任层级上。
2
STEP 2 / CODE REVIEWMANDATORY

逐文件审查

协议里唯一标了强制的一步：Read ALL files in the skill. 不是读入口文件，是读每一个文件——脚本、示例、元数据都算——然后对照 14 条红线逐条核。

  • →读：SKILL.md + 脚本 + 示例 + 元数据 + 资源文件
  • →核：14 条红线逐条对照，命中即拒
  • →查：混淆 / 编码 / 隐藏的执行路径
产出RED FLAGS 清单——「无」，或逐条列出命中的条目与出处。
3
STEP 3 / PERMISSION SCOPE

权限范围

把 skill 真正会碰到的东西列出来，并回答一个判断性问题： 这些权限相对它声称的用途，是不是最小必要？

  • ☐需要读哪些文件？
  • ☐需要写哪些文件？
  • ☐会执行什么命令？
  • ☐是否需要联网？连到哪里？
  • ☐范围是否为其用途所最小必需？
产出Files / Network / Commands 三类权限清单，逐条可核。
4
STEP 4 / RISK CLASSIFICATION

风险定级

四级风险，四级处置权限。这一步产出的不是一个分数，而是谁有权拍板—— 🔴 及以上，决定权从 agent 手里移交给人。

  • 🟢LOW —— 基础核查，可直接安装
  • 🟡MEDIUM —— 必须完整读码，附条件安装
  • 🔴HIGH —— 人工批准
  • ⛔EXTREME —— 禁止安装
产出RISK LEVEL + VERDICT。
出口 · SKILL VETTING REPORT

四步走完，产出一份固定六段的文本报告。报告本身不具强制力——它不拦截安装，也不修改任何代码。 它做的是把权限和定级摊在台面上，让「装不装」这个决定有依据、有留痕。

⚠️ INSTALL WITH CAUTION对应 🟡 MEDIUM

⚠️Step 2 的强制条款，在真实 skill 上会撞车

skill-vetter 要求读完待审 skill 的每一个文件；而在 anthropics/skills 里，有的 skill 明确要求你 别读它的源码。两个都装上，agent 会收到方向相反的指令。

skill-vetter · SKILL.md 第 33 行
Read ALL files in the skill.
同一条步骤的标题即标注 Code Review (MANDATORY)。
webapp-testing · SKILL.md 第 14 行
DO NOT read the source until you try running the script first and find that a customized solution is abslutely necessary. … They exist to be called directly as black-box scripts rather than ingested into your context window.
原文里 abslutely 是拼错的（应为 absolutely）——说明这里引的是原文，不是转述。
这不是谁对谁错。skill-vetter 把「读源码」当成安全前提，webapp-testing 把「不读源码」当成上下文预算前提， 两个目标函数相反。协议本身没给取舍规则，所以 Step 2 在实操中不能当机械规则执行： 遇到明确声明黑盒调用的 skill，要么接受读码带来的上下文成本，要么换一种更省的取证方式，要么干脆放弃它。

ADOPTION · 谁在用

谁在装 skill 之前，会先跑一遍它

skill-vetter 不替你做某一类具体的活。它处理的是信任问题—— 当一个 skill 来自你没读过的仓库、不认识的人，或者一次群聊转发， 你需要一个能复述、能归档的判断依据。下面三类人最常需要它。

01 主力
独立开发者 / agent 开发者
重度依赖第三方 skill 生态。装之前会扫一眼作者和更新时间， 但基本不会逐行读别人的代码——那是几百上千行的事。
拿到什么 一份能复述的裁决：🟢 可装 / 🔴 需人工批准，而不是「感觉还行」。
02
平台的安全与合规团队
需要把「我们评估过这个 skill」变成证据链，而不是一句口头结论。 报告结构固定，可归档、可比对、可审计。
拿到什么 统一的审查模板与逐次留痕；风险定级本身已绑定处置权限，可直接写进准入流程。
03
多 agent 系统的编排者
多个 agent 之间会互相推荐 skill。你需要一条硬约束—— 不许装未审查的代码，而不是靠每个 agent 自觉。
拿到什么 把 Step 2「读全部文件（MANDATORY）」接到安装动作之前，作为准入前置条件。
✕什么时候别用它
  • 别当沙箱用——它只读、只报告，不阻断执行、不改代码。
  • 别当防篡改用——不校验哈希，审查完到安装之间仍有窗口。
  • 别指望扫出所有坏东西——红线靠通读匹配，变量拼接、间接调用识别不出。
  • 别照搬红线表——「访问 MEMORY.md / USER.md 等身份文件」这类条目，在本地 agent 环境会大面积误报。

把它放在安装动作之前。

skill-vetter 是一份纯 Markdown 协议——没有脚本、没有依赖、没有网络调用。 放进 skill 目录，agent 下一次读到它时就能用。

它不会替你装，也不会替你执行。它给的是一个可以拍板的结论。
