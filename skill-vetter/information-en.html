Scrutiny scales with provenance: official skills get less, unknown sources get maximum, anything requesting credentials gets a human.

5 levels · credentials always require human approval

Risk tiers and the action each one forces

🟢 LOWNotes, weather, formattingBasic review · install OK
🟡 MEDIUMFile ops, browser, APIsFull code review required
🔴 HIGHCredentials, trading, systemHuman approval required
⛔ EXTREMESecurity configs, root accessDo NOT install
The verdict line offers 3 outcomes — SAFE TO INSTALL / INSTALL WITH CAUTION / DO NOT INSTALL — which are not a one-to-one mapping of the 4 tiers. A package can be 🟢 LOW and still warrant caution; that gap is where the residual risk lives.

What the 14 patterns actually look for

Egresscurl / wget to unknown URLs · IP-based calls · data sent out
Credentialstokens, API keys, ~/.ssh, ~/.aws, cookies, credential files
Identity filesMEMORY.md · USER.md · SOUL.md · IDENTITY.md
Executioneval / exec on external input · base64 decode · sudo
Concealmentobfuscated or minified code · unlisted package installs · writes outside workspace
These are static text patterns, not behavioural analysis. A pattern present in the source is caught; an equivalent behaviour assembled at runtime is not.
04 · Workflow

Four steps, then and only then: install or don't.

The protocol is sequential. Step 2 is marked mandatory in the source — a review that skips the file read is not a review.

01

Source Check

Establish provenance: where it came from, who published it, how widely it is used, when it last changed, what others reported.

5 questions · provenance recorded before files are opened
02

Code Review

Read all files. Match against the 14 reject patterns — egress, credentials, identity files, dynamic execution, concealment.

14 patterns · any hit = reject immediately
03

Permission Scope

Enumerate reads, writes, commands, and network endpoints. Judge whether the scope is minimal for the stated purpose.

5 checks · minimality is the test
04

Risk Classification

Assign a tier, bind it to the required action, emit the fixed report, and state a verdict the user can act on.

4 tiers · verdict field is mandatory
Important boundary

This protocol answers "what does this package touch, and is that acceptable?" — not "does it do its job well?" A package that passes can still be useless; a package that fails on a pattern is rejected regardless of how useful it looks. Review quality also depends on the reviewing agent actually opening every file — the skill guides the review, it does not execute a scanner.

06 · Security · Compatibility · Reliability

The reviewer itself has nothing to hide.

Audited before use, in the same way it audits others. What follows is what the file actually contains.

Security audit · 7 checks

  • ✓0 lines of executable codepure Markdown instructions
  • ✓No install hooks or scriptsno pre/post install actions
  • ✓No dependency installationno pip / npm / requirements
  • ✓No outbound network callscommands shown are for the user to run
  • ✓No credential or file accessreads only what the agent opens
  • ✓4 files totalSKILL.md · _meta.json · skill-card.md · assets/
  • ✓138 lines, single file of logicreadable end to end in one sitting

Reliability · design constraints

  • ✓Step 2 marked mandatory in sourcethe file read cannot be treated as optional
  • ✓14 patterns enumerated, not summarisedeach one matchable or clearable
  • ✓Fixed report skeleton7 field groups, verdict required
  • ✓Verdict is a closed set3 outcomes, no free-form hedge
  • ✓Refusal is a valid output"do not install" is built in, not a failure
  • ✓Human escalation definedcredentials always require approval

Known limitations · 6

  1. Static only. It inspects the text of a package revision. It does not execute code, resolve obfuscated payloads, or observe runtime behaviour.
  2. It does not detect malware. A clean result means no listed pattern matched — not that the package is benign.
  3. Publisher trust is out of scope. It records who published the package; it cannot verify who that actually is.
  4. Revisions reset the result. A hash-recorded review covers one upload. A later release requires a fresh pass.
  5. Popularity is not evidence. Stars, downloads, and clean registry labels are context, not proof.
  6. Quality of review tracks the reviewing agent. The skill structures the work; it cannot force the agent to open every file.
07 · Who it's for

Built for the moment just before install.

Anyone can read a registry page. This is for the step where someone has to decide whether that is enough.

01

Agent operators

People who install third-party skills into a working agent.
Run it before every install from an unfamiliar source — the report takes one pass and stays on record.
02

Skill authors

People publishing packages that others will be asked to trust.
Pre-audit your own package against the 14 patterns so reviewers find nothing to flag.
03

Team leads

Anyone accountable for what runs on other people's machines.
Require the fixed report as the install artifact — no report, no install.
04

Security reviewers

People who need a repeatable first pass, not a tool that replaces judgment.
Use it as triage: it narrows what deserves a full read, and it says so.
