01 · Skill / 工作流诊断

AI 工作流跑得起来就上线？
这个 Skill 专查那些
出事才露头的隐患

给自建 AI 工作流做上线前体检。把提示词原文、工具清单或 agent 配置交进去，得到五个维度的 1 到 5 分、25 分制总评，以及按严重度排好的整改动作。

提示词、Skill、多 Agent 流水线，搭完只要能跑通，大多数人就当它能用了。会让它在上线后出问题的结构性隐患，其实在跑通的那一刻就已经在里面了。

diagnose 是一个诊断类 Skill。它按 Prompt 质量、上下文效率、工具健康度、架构适配度、安全与可靠性五个维度各打 1 到 5 分，输出一张 25 分制评分卡，外加按严重程度排序的关键发现和整改动作。

它不给你一份通用检查清单。评分要落到具体层级，每条发现都要能指出依据。

02 · Before / After

三处变化：判断依据、产出形态、能审的规模

每一组左边是用它之前的状态，右边是诊断之后拿到的结果。

01

判好坏的依据

Before

一个 AI 工作流搭完之后，能用来判断它好坏的信号通常只有一个：跑起来没报错。有没有定义输出格式、失败之后会不会恢复、成本有没有上限，只能靠事后回忆。

After

五个维度各拿到 1 到 5 分，每一维都写明扣在哪。低于 3 分的维度直接标黄，告诉你问题落在哪一层。

从「看起来没问题」，变成「知道哪一维只有 2 分，以及为什么」。

02

从一段描述到一份报告

Before

问题散在提示词、脚本、配置和记忆里。要复盘一次只能重读一遍所有文件，而且没有固定格式可以对照，读完还是只有印象。

After

一份 25 分制报告：五维评分条加总评，三条按严重程度排序的关键发现，每条发现下面给出对应的整改动作。

从「我印象里这块可能有点问题」，变成「这三条是现在就该改的」。

03

能审的规模

Before

提示词还能靠经验看两眼，一旦脚本变多、层级变深，就没有通用的检查办法。文件越多，漏掉的东西越多。

同一把评分尺能量三种量级：单文件提示词、多阶段门控流水线、带脚本和外部副作用的系统。

从「只审得了提示词」，变成「从 1 个文件到 52 个文件的系统都能审」。

03 · Pain Point / Use Case

让 AI 工作流出问题的，通常不是它跑不通

下面三种处境都来自真实的工作流，也都不是假设。

处境一 · 写单文件 Skill 的人

文档里写着的依赖，包里没有

一份 123 行 / 7,535 字节的提示词 Skill，逻辑清楚、步骤完整，路径和版本号都逐个给到了，看起来是能直接用的成品。

但它指向了六个「已随包提供、直接复制即可」的脚本，而那六个文件从来不在包里。写的人自己机器上有，读者机器上没有。

这类问题不会让 Skill 报错，只会让读者照做到第二步就停下，然后以为是自己环境的问题。
处境二 · 维护多阶段流水线的人

流程要联网，但没声明过联网能力

一条带门控的流水线，输出契约、禁用词表、自检清单都写得比大多数人认真，防编造规则甚至分了四级证据。

可它把「在可联网时搜索官方页面核验链接」写进了必做流程，而整套文档从头到尾没有声明过任何工具能力。

在能联网的宿主上它会去搜，在不能的宿主上它就卡在那里。同一份工作流，换一个环境就换了行为，而使用者不会收到任何提示。
处境三 · 做会动真钱系统的人

代码能做到的，比文档写着的多

一个覆盖五家交易所、带 37 个脚本的执行系统，凭据只走环境变量，下单前强制用户确认，前置校验一条不少。

但其中一个标记为可选的脚本，支持向任意 URL 发送 POST 数据，也支持执行环境变量指定的外部命令。这两条通道没有出现在它的能力声明里。

使用者按文档读到的能力面，比代码实际具备的能力面小。而这类缺口在单次功能测试里根本触发不到。

这三件事都不是 bug

它们有同一个特征：跑起来没问题，测试也过，只有在特定的环境下、特定的调用路径上才会露出来。所以它们不会被任何一次「能用」的验证拦下来。

而平时手上的判断工具都不在这个层面上。提示词技巧类的文章给的是通用清单，不看你这一条工作流；代码检查工具看得懂语法，看不懂「这段提示词有没有定义输出格式」；自己重读一遍文件，读到的往往是写的时候的想法，而不是结构上的缺口。

结果是延迟暴露：问题不在搭建的那一刻暴露，而是在别人开始用的时候、在上线之后、在它开始动真钱的时候暴露。

04 · Transition

缺的不是更多经验，而是一次按固定维度做的检查。结构性的问题只有在被逐项追问时才会显形：这一段有没有定义输出？工具声明和实际行为一致吗？失败之后会发生什么？成本有没有上限？

diagnose 就是这个追问过程。它把检查拆成固定的五个维度，每次都问同样的问题，因此两次诊断的分数落在同一把尺上，改完之后能看出是变好还是变差。

05 · Solution

你提供工作流，它逐维给分并说明依据

从输入到输出只有三步，中间没有需要你配置的东西。

输入

下面四样给其中一样就能开始，给得越具体，发现越准。

  • 工作流描述
  • 提示词原文
  • 工具清单
  • Agent 配置
评估 · 五个维度
D1

Prompt 质量

1 到 5 分

角色、上下文、指令、输出区是否各就各位，输出格式是明写还是隐含，边界情况有没有交代，有没有明显的反模式。

D2

上下文效率

1 到 5 分

预算有没有规划过，关键信息放在开头还是结尾，状态和记忆是显式管理还是靠默认，长度是否与任务相称。

D3

工具健康度

1 到 5 分

工具数量在不在可用区间，描述是否具体，错误处理有没有，输入、输出、错误是否都定义了，重复调用是否安全。它还会区分项目自己配置的工具和 agent 自带的工具，只对前者计账。

D4

架构适配度

1 到 5 分

单 Agent 够不够、多 Agent 是不是真的需要，边界是否重叠，交接有没有协议，决策有没有留痕，成本有没有预算。

D5

安全与可靠性

1 到 5 分

输入校验、输出过滤、成本上限、失败恢复、评估策略。它会按数据的实际暴露范围来判断风险，而不是一律套最高标准。

输出
固定三件
  1. 一张 25 分制评分卡，五个维度各一条评分条加总评
  2. 三条按严重程度排序的关键发现
  3. 每条发现对应的整改动作
06 · Real Cases / Outputs

同一把尺，三种量级

下面三个案例都是本次会话按它的五个维度实跑的真实工作流，分数与发现可以逐条核对。

CASE 01

单文件提示词 Skill

1 个文件 · 123 行 · 7,535 字节
输入

一份单文件提示词 Skill，职责是用真实无头浏览器做网站审计，要求每条结论都能追到数字、截图或原始响应。

输出

17 / 25 分。最致命的一条是随包依赖缺失：流程里指明六个可复用脚本写在 audit/ 目录、直接复制即可，而全盘检索这六个文件名 0 命中，该目录也不存在。同一份文档里另外两条环境声明（Chromium 二进制路径、playwright-core 的安装位置）经核验都是真的。

真和假混在同一段里。整段信任会漏掉断点，整段怀疑会误伤两条正确的声明，只能逐条查。这正是人工重读最容易放过的地方。

07 · Core Advantages

四条能落到用户身上的差异

01

评分落到层级，不是给个感觉

五个维度分别打分，所以一个「2 分」能指向具体是哪一层出了事。三个实测案例的工具健康度都是 2 分，成因却完全不同：一个是依赖缺失，一个是工具契约空白，一个是工具过载。

一句笼统的「工具太多」，会同时误判前两个。分层打分才不会。

02

每条发现都要给依据

它的规则要求每个维度都给出具体发现，而不是只给一个分数。三个案例里的「六个脚本 0 命中」「35,363 字节固定预读」「未声明的 POST 通道」都是查得到出处的东西。

拿到报告的人可以自己去核对，不需要先相信评分人的判断。

03

同一把尺，可以复测

维度、分值区间和五档评分表的含义都是固定的。改动之后再测一次，两个分数落在同一把尺上，能看出是变好还是变差，而不是每次都从零开始重新判断。

这是通用检查清单给不了的，因为清单没有分数。

04

只对你能控制的工具计账

工具健康度里专门有一条：区分项目自己配置的工具和 agent 自带或全局安装的工具，只对前者扣分。否则一份报告会把宿主环境的工具数量算到你头上，看着问题很多，实际一个都改不了。

报告里剩下的每一条，都是你能动手改的。

08 · Why It Matters

diagnose 想改变的不是某一次评审的结果，而是发现问题这件事发生的位置。

在「跑通」和「交出去」之间加一道固定检查，问题就从「别人用到的时候」提前到「还没交出去的时候」。而因为维度是固定的，这道检查可以反复用：改完提示词再测一次，加了脚本再测一次，换了宿主再测一次，每次的分数都落在同一把尺上。

一次诊断留下的不只是三条整改动作，还包括你自己的工作流哪一维最薄。知道这一点之后，下一次搭新的工作流时，你会先把那一维补上。
